## 一、MCP 协议的核心角色

MCP（Model Context Protocol）是一个**客户端-服务器架构**的协议，涉及三个核心角色：

```
┌─────────────────────────────────────────────────────────────────────┐
│                        MCP 完整通信架构                              │
│                                                                     │
│   ┌──────────┐          MCP 协议           ┌──────────────────┐    │
│   │          │◄────────────────────────────►│                  │    │
│   │   Host   │                              │  MCP Server      │    │
│   │ (主持人)  │   JSON-RPC 请求/响应/通知     │  (本项目)        │    │
│   │          │◄────────────────────────────►│                  │    │
│   └────┬─────┘                              └────────┬─────────┘    │
│        │                                               │              │
│        │  通过 Transport 传输                         │  调用        │
│        ▼                                               ▼              │
│   ┌──────────┐                              ┌──────────────────┐    │
│   │  Client  │                              │   Plugins        │    │
│   │ (客户端)  │                              │  (工具插件)       │    │
│   └──────────┘                              │  weather.so      │    │
│                                             │  code-review.so  │    │
│   Host = 管理 Client 的容器                  └──────────────────┘    │
│   Client = 具体的 AI 连接（如 Claude Desktop）                       │
│   Server = 工具服务的提供者（我们写的这个 C++ 程序）                   │
└─────────────────────────────────────────────────────────────────────┘
```

### 各角色职责

| 角色 | 中文名 | 职责 | 例子 |
|:---:|:---:|:---|:---|
| **Host** | 主持人 | 管理多个 Client 的生命周期，负责协调整个对话上下文 | Cherry Studio、Claude Desktop |
| **Client** | 客户端 | 和 Server 建立 1:1 的持久连接，发送请求、接收响应 | 某个具体的 AI 对话窗口 |
| **Server** | 服务器 | 暴露工具（Tools）、提示词（Prompts）、资源（Resources），响应 Client 的调用 | **本项目（C++ 实现）** |

### MCP 协议中的三类能力

```
┌─────────────────────────────────────────────────────┐
│                 MCP Server 暴露的能力                │
├─────────────────────────────────────────────────────┤
│                                                     │
│   1. TOOLS（工具）  — AI 可以调用的函数              │
│      例如：查天气、查数据库、调用意愿                 │
│      方法：tools/list → 列出所有工具                │
│            tools/call → 调用某个工具                │
│                                                     │
│   2. PROMPTS（提示词）— 预定义的提示模板             │
│      例如：帮我代码审查、生成测试用例                 │
│      方法：prompts/list → 列出所有提示词            │
│            prompts/get → 获取某个提示词详情         │
│                                                     │
│   3. RESOURCES（资源）— AI 可读取的上下文数据        │
│      例如：文件内容、数据库 schema                   │
│      方法：resources/list → 列出所有资源            │
│            resources/read → 读取某个资源            │
│                                                     │
└─────────────────────────────────────────────────────┘
```

## 二、这个项目是什么？

### 项目定位一句话总结

> **本项目是一个用 C++20 实现的高性能 MCP Server 框架**，它通过插件化架构和热插拔技术，让 AI（由 Cherry Studio 等 Host 管理）能够安全、高效地调用本地系统工具。

### 解决什么问题？

```
痛点：AI 模型无法直接访问本地工具和数据

┌──────────────┐     MCP 协议      ┌──────────────┐     dlopen      ┌──────────────┐
│  AI 模型     │◄─────────────────►│   我们的      │◄───────────────►│  工具插件     │
│  (LLM)       │   JSON-RPC        │   C++ Server │   .so / .dll    │  (业务逻辑)   │
└──────────────┘                   └──────────────┘                  └──────────────┘

        │                              │
        │  "帮我查一下北京天气"          │  返回 JSON 结果
        │─────────────────────────────►│────────────────────────────►
```

### 技术指标

| 维度 | 描述 |
|:---|:---|
| **语言** | C++20 |
| **版本** | 0.8.0 |
| **传输协议** | Stdio（本地）、SSE（HTTP 长连接）、HTTP Stream（会话制） |
| **插件机制** | 动态链接库热插拔（Linux: .so，Windows: .dll） |
| **线程安全** | 快照 + 引用计数，无锁访问插件列表 |
| **日志** | AixLog（跨平台日志库） |

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                          完整调用链路                                        │
│                                                                            │
│  1. [Host/Client]                                                         │
│     发送 JSON-RPC 请求：                                                   │
│     {"jsonrpc":"2.0","method":"tools/call","params":{"name":"weather",..}}
│     │                                                                     │
│     ▼ Transport 层                                                         │
│  2. StdioTransport / SseTransport / HttpStreamTransport                   │
│     Read() → 解析原始数据流                                                │
│     │                                                                     │
│     ▼ Server 层                                                            │
│  3. Server::OnMessage(message)                                            │
│     → HandleRequest() → 查询路由表 method→handler                         │
│     │                                                                     │
│     ▼ PluginsLoader                                                        │
│  4. loader->GetPluginsSnapshot()                                          │
│     → 遍历 PluginEntry 向量                                                │
│     → 调用 plugin->instance->HandleRequest(json)                          │
│     │                                                                     │
│     ▼ Plugin 层（weather.so 等）                                          │
│  5. 实际业务逻辑执行                                                        │
│     → 调用外部 API（如 open-meteo.com 天气接口）                           │
│     → 返回 JSON 结果 {"content":[{"type":"text","text":"北京：晴，26°C"}]}
│     │                                                                     │
│     ▼ Server 层                                                            │
│  6. 构造 MCP 响应格式                                                       │
│     → 写回通知队列（异步，不阻塞）                                          │
│     │                                                                     │
│     ▼ Transport 层                                                         │
│  7. Write(response) → JSON-RPC 响应发回 Client                           │
│     {"jsonrpc":"2.0","id":1,"result":{...}}                               │
└─────────────────────────────────────────────────────────────────────────────┘
```

```cpp
// 传输层抽象接口 - 统一读写接口
class ITransport {
    virtual bool Start() = 0;
    virtual void Stop() = 0;
    virtual std::pair<size_t, std::string> Read() = 0;        // 同步读
    virtual void Write(const std::string& json_data) = 0;      // 同步写
    virtual std::future<std::pair<size_t, std::string>> ReadAsync() = 0;
    virtual std::future<void> WriteAsync(const std::string& json_data) = 0;
};
```

**两个关键设计**：
1. **OverrideCallback**：允许运行时替换默认命令处理逻辑（本项目用它把 tools/list/call 替换为从 PluginsLoader 获取结果的逻辑）。
2. **通知队列 + Writer 线程**：通知发送不阻塞请求处理线程。

### 4.3 PluginsLoader 层

插件热插拔的核心，最能体现 C++ 工程能力。

**核心类**：[PluginsLoader.h](file:///e:/STUDY/Work_C/00AA-Start/Git_pull_mcp/mcp_server/src/loader/PluginsLoader.h)

```
PluginsLoader 插件加载流程
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
启动阶段
│
├─ 扫描插件目录（plugins/）
│
├─ 复制到 staging 副本（.staging/libxxx_timestamp.so）
│   目的：加载和原文件分离，允许原子替换
│
├─ dlopen() 加载动态库
│
├─ dlsym() 获取 CreatePlugin / DestroyPlugin 函数
│
├─ 调用 CreatePlugin() 创建插件实例
│
├─ 调用 Initialize()
│
└─ 注册到 PluginEntry 向量

运行时热插拔（后台线程每 5 秒扫描）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│
├─ 检测到新 .so 文件 → 加载新插件
│
├─ 检测到文件 mtime/size 变化
│   → 先加载新版本
│   → 成功后原子替换旧版本
│
└─ 检测到文件被删除
    → 标记卸载
    → 等所有快照引用释放后自动析构
```

**并发安全策略**：
```
请求线程（读）                      后台监控线程（写）
     │                                    │
     │ GetPluginsSnapshot() ─────────────►│
     │ 获取 shared_ptr<const PluginEntry> │
     │ 在无锁状态下执行插件代码             │
     │ （因为快照是只读的）                │
     │                                    │ 检测到文件变化
     │                                    │ 加载新版本
     │                                    │ 替换 shared_ptr
     │                                    │（旧 PluginEntry 引用计数-1）
```

### 4.4 Plugin 层

具体的业务逻辑插件，通过 C 接口与宿主交互。

**插件接口**：[PluginAPI.h](file:///e:/STUDY/Work_C/00AA-Start/Git_pull_mcp/mcp_server/src/interface/PluginAPI.h)

```cpp
// 每个插件必须导出的两个函数
extern "C" {
    PluginAPI* CreatePlugin();   // 创建插件实例
    void DestroyPlugin(PluginAPI*); // 销毁插件实例
}

// 插件类型
typedef enum {
    PLUGIN_TYPE_TOOLS = 0,      // 可调用工具
    PLUGIN_TYPE_PROMPTS = 1,    // 提示词模板
    PLUGIN_TYPE_RESOURCES = 2,  // 可读资源
} PluginType;

// 插件 API 结构体（函数指针集合）
typedef struct {
    const char* (*GetName)();
    const char* (*GetVersion)();
    PluginType (*GetType)();
    int (*Initialize)();
    char* (*HandleRequest)(const char* request);  // 处理请求
    void (*Shutdown)();
    int (*GetToolCount)();
    const PluginTool* (*GetTool)(int index);
    // ... prompts, resources ...
    NotificationSystem* notifications;  // 主动通知系统
} PluginAPI;
```

## 五、面试可用的全局总结

### 一句话项目介绍

> 这是一个**基于 C++20 的高性能 MCP Server 框架**，通过插件化架构和运行时热插拔技术，让 AI Agent 能够安全、低延迟地调用本地系统工具。

### 技术选型理由（面试加分项）

| 技术点 | 为什么用 | 面试怎么答 |
|:---|:---|:---|
| **C++20** | 零开销抽象 + 现代语法（coroutine/concepts） | "工业级场景对延迟敏感，C++ 相比 Python 有数量级的性能优势，且能精细控制内存生命周期" |
| **dlopen/dlsym** | 运行时动态加载 .so，不侵入主进程 | "通过原生动态链接机制实现插件隔离，新插件加载失败不影响主服务" |
| **快照机制** | 读不用锁，写不用等 | "插件列表通过 shared_ptr 快照分发，请求线程无锁执行，后台线程原子替换，旧插件引用计数归零后自动析构" |
| **staging 副本** | 原子更新 | "先复制到临时文件再加载，文件替换时主进程感知的是不同的路径，天然支持回滚" |
| **OverrideCallback** | 解耦插件逻辑和协议处理 | "Server 不直接依赖 PluginsLoader，而是通过回调注入，这种依赖注入设计让核心逻辑可测试" |
